# Task E (bonus) — Шлях 3: сервер, якому потрібен токен, підключений безпечно

**Сервер:** GitHub MCP — remote (HTTP), `https://api.githubcopilot.com/mcp/x/repos/readonly`

Це єдиний сервер у моїй конфігурації з **справжнім доступом до зовнішньої
системи**. `catalog` читає локальний JSON, `filesystem` — локальні файли,
`fetch` і `context7` не мають облікових даних узагалі. Тут же — токен до мого
акаунта GitHub, тобто вперше в цій домашці ціна помилки виходить за межі
робочої машини.

---

## Які права дали токену

**Fine-grained PAT**, а не classic:

| Параметр | Значення |
|---|---|
| Тип | Fine-grained personal access token |
| Repository access | **Only select repositories** → лише `Fyfar/2026-udc-06-mcp-hw` |
| Contents | **Read-only** |
| Metadata | **Read-only** (обов'язкове, вмикається автоматично) |

## Які права свідомо НЕ дали

| Не дано | Чому |
|---|---|
| **Contents: Read and write** | Завданню потрібно лише читати історію та файли форку. Запис відкрив би пряму дорогу від prompt injection до коміту в мій репозиторій. |
| **Pull requests, Issues** | Не потрібні для сценарію. Кожен дозвіл — це ще один спосіб діяти від мого імені. |
| **Actions, Workflows** | Найнебезпечніше з усього списку: право писати workflow = виконання довільного коду в CI від мого імені. |
| **Administration** | Керування самим репозиторієм — ніколи не потрібне агенту. |
| **All repositories** | Дефолт при створенні токена. Свідомо звужено до одного форку: компрометація токена не має торкатися інших моїх репозиторіїв. |
| **Organization-level permissions** | Токен не має доступу до жодної організації. |

## Дві незалежні межі, а не одна

Це головна ідея цього шляху. Доступ звужено **двічі, різними механізмами**:

| # | Межа | Де діє | Хто її забезпечує |
|---|---|---|---|
| 1 | Toolset у URL — `/x/repos/readonly` замість дефолтного `/mcp/` | Набір інструментів, які сервер узагалі віддає | GitHub, на своєму боці |
| 2 | Права самого PAT — один репозиторій, Read-only | Що дозволено зробити з будь-яким запитом | GitHub, на своєму боці |

**Перевірено наживо:**

- **Межа 1.** Пошук у наборі інструментів сесії за `create_or_update_file`,
  `push_files`, `create_branch`, `delete_file`, `merge`, `fork` не повернув
  **жодного** записувального інструмента — тільки читальні. Виміряне мною — 13
  read-інструментів і **0** записувальних. Для контрасту: дефолтний `/mcp/` дає
  44 інструменти, з них 14 записувальних — але це **не мій вимір**, я його
  свідомо не піднімав, щоб не тягнути ці 14 у сесію.
- **Межа 2.** Навіть якби я помилився в URL і підняв дефолтний toolset,
  записати нічим: токен не має права `Contents: write`.

Порівняння з `filesystem` тут прямо повчальне. Там «звуження» було
**аргументом у моєму конфізі** — і воно мовчки не спрацювало
([`mcp/SECURITY.md`](./mcp/SECURITY.md) §2.1). Тут звуження живе **на боці
GitHub**, тобто його не можна скасувати редагуванням файлу на моїй машині —
ані мною, ані агентом, ані тим, хто дістався до репо. Це і є різниця між
декларацією наміру і межею.

## Як саме токен потрапляє в конфіг

У `.mcp.json` — **тільки посилання на змінну**, ніколи значення:

```json
"github": {
  "type": "http",
  "url": "https://api.githubcopilot.com/mcp/x/repos/readonly",
  "headers": {
    "Authorization": "Bearer ${GITHUB_PERSONAL_ACCESS_TOKEN}"
  }
}
```

Ланцюг такий:

1. Реальне значення живе в `.env`, який у `.gitignore`.
2. У репо комітиться `.env.example` — з тим самим ключем і **порожнім**
   значенням (`GITHUB_PERSONAL_ACCESS_TOKEN=`) плюс коментар, які саме права
   потрібні.
3. Claude Code розширює `${...}` зі **свого власного оточення** і `.env`
   **не читає**. Тому хост запускається так:

   ```sh
   set -a; source .env; set +a && claude
   ```

   Це не косметика: без цього кроку сервер отримає порожній заголовок
   `Authorization` і мовчки не автентифікується.

## Доказ, що секрет не в репозиторії

```bash
git grep -nE "ghp_[A-Za-z0-9]{20,}|github_pat_[A-Za-z0-9_]{20,}|sk-[A-Za-z0-9]{20,}" || echo "clean"
```

```text
clean
```

Додатково:

- `git ls-files .env` → файл не відстежується git-ом;
- `git check-ignore .env` → ігнорується (`.gitignore`, рядок `.env`);
- у `.env.example` значення порожнє — комітиться тільки ім'я змінної.

## Доказ, що сервер справді працює

`list_commits` на `Fyfar/2026-udc-06-mcp-hw` повернув реальну історію:

```text
891a80e  Fix defects found by the homework dry run
156ef09  WS6 homework: MCP over a seeded catalog domain
```

Тобто токен дійсний, заголовок підставився, звужений toolset читання не ламає.

## Висновок: що змінилось в оцінці ризику

**1. З'явився перший актив, який не належить цій машині.** Доки всі сервери
були локальні й безключові, найгірший сценарій обмежувався робочою копією.
Токен виводить наслідки назовні: тепер компрометація сесії — це подія в моєму
GitHub-акаунті, а не лише в теці репозиторію.

**2. Токен виявився надійнішою межею, ніж конфіг.** Task A навчив, що
вузький шлях у `.mcp.json` — це декларація, яку протокол може скасувати
(§2.1). Права токена скасувати нічим: вони перевіряються на боці GitHub, поза
досяжністю всього, що живе в цьому репозиторії. Тому послідовність правильна
саме така — **спочатку звузити токен, потім конфіг**, а не навпаки.

**3. Але сам факт наявності токена додав ризиків, яких раніше не було:**

- він потрапляє в оточення процесу-хоста, а отже й **усіх stdio-серверів**,
  запущених із нього (§2.7) — `filesystem` і `fetch` бачать змінну, якої їм
  ніколи не було потрібно;
- це **remote-сервер**, тож описи його інструментів можуть змінитися між
  запусками без сліду в моєму git (§2.5);
- у парі з `fetch` він робить exfiltration-ланцюг предметнішим: тепер є що
  виносити, а не лише синтетичні дані про клавіатури.

**4. Що лишилось незробленим.** Політика ротації та строк дії токена не
задокументовані в цьому репо — я знаю, що PAT fine-grained і має expiry, але
не зробив із цього процедуру. Для навчального репо з read-only токеном на один
публічний форк приймаю; для будь-чого серйознішого це було б першим пунктом
доробки разом із полем `env` посерверно (§4, п. 3).

**Одним рядком:** підключати сервер із токеном безпечно — це не «сховати ключ
у `.env`». Ключ у `.env` розв'язує лише проблему git. Реальну межу дають
**права токена**, видані так вузько, щоб компрометація конфігу, хоста чи самої
моделі нічого не змінювала.
