# Threat model MCP-інтеграцій (Task C)

## 1. Що до чого має доступ

| Сервер | Дані/ресурси, до яких дістає | Секрети | Може писати? | Довіра до автора |
|---|---|---|---|---|
| filesystem | `./app/data` | немає | так, у межах дозволеного каталогу | офіційний MCP server |
| memory | власний persistent knowledge graph | немає | так, може створювати та змінювати memory entities/relations | офіційний MCP server |
| catalog | `app/data/catalog.json` через доменні функції `app/dist/index.js` | немає | ні | свій код |

## 2. Ризики, які я вважаю реальними для цієї конфігурації

- **Prompt injection через дані.** Жоден із трьох підключених серверів не отримує контент з вебу або інших зовнішніх джерел. Однак `filesystem` читає `app/data`, а `catalog` повертає дані з `catalog.json`. Якщо в репозиторій потрапить недовірений текст, модель потенційно може інтерпретувати його як інструкцію. Ризик зараз обмежений локальними даними навчального репозиторію.

- **Занадто широка область доступу.** `filesystem` є найбільш ризиковим сервером, оскільки має файлові tools із можливістю запису. Його scope навмисно обмежено `./app/data`, тому він не отримує доступу до всього репозиторію, домашнього каталогу чи файлової системи. `catalog` має ще вужчий доступ: тільки до каталогу через імпортовані доменні функції. `memory` не має доступу до файлів проєкту, але може читати та змінювати власний knowledge graph.

- **Витік секретів.** Жоден із трьох MCP-серверів не потребує токенів або інших секретів. У `.mcp.json` немає credentials або literal secrets. Через вузький scope filesystem він також не має доступу, наприклад, до файлів із домашнього каталогу користувача.

- **Зміна поведінки сервера після встановлення.** `filesystem` та `memory` запускаються через `npx -y` без зафіксованої версії пакета. Нові версії цих пакетів можуть змінити набір tools або їх поведінку без змін у цьому репозиторії. Це supply-chain/reproducibility risk. Власний `catalog` сервер запускається з локально зібраного коду, але його npm dependency `@modelcontextprotocol/server` також задана через semver range.

- **Дії з побічним ефектом.** Власний `catalog` MCP є read-only: `search_inventory` і `low_stock` лише читають дані, а resource `inventory://catalog` лише повертає summary. `filesystem` має tools, здатні змінювати файли всередині `./app/data`. `memory` також має side effects: наприклад, під час перевірки через `create_entities` було створено persistent entity. Тому не всі підключені MCP є read-only, навіть якщо власний сервер таким є.

## 3. Що я зробив, щоб це зменшити

- `filesystem` обмежено точним шляхом `./app/data`, а не всім репозиторієм, домашнім каталогом користувача або `/`.
- Для project-level MCP configuration використовується `.mcp.json`, тому область доступу та підключені сервери явно видно в репозиторії.
- Жоден із підключених серверів не потребує секретів, тому `.mcp.json` не містить credentials.
- Власний `catalog` MCP реалізовано як read-only adapter: він не має tools для запису, видалення даних або мережевих запитів.
- Бізнес-логіка в `catalog` MCP не дублюється: сервер використовує `loadCatalog`, `searchProducts`, `lowStock`, `categories` та `inventoryValue` з `app/dist/index.js`.
- Перед підключенням до Claude Code власний сервер перевірено напряму через MCP Inspector: `tools/list` показав два tools, а `resources/list` — `inventory://catalog`.
- Підключення також перевірено в Claude Code: `catalog` підключився з 2 tools, а запит про товари для reorder викликав саме `Catalog [low_stock]`.

## 4. Що лишилось прийнятим ризиком

Для `filesystem` та `memory` не зафіксовані конкретні npm-версії, тому майбутній запуск через `npx` може використати новішу версію сервера з іншою поведінкою. Для навчального репозиторію це прийнятно, але в production версії слід pin-ити та контролювати їх оновлення.

`filesystem` залишається сервером із write-capabilities у межах `./app/data`. Scope суттєво зменшує потенційний impact, але не робить сервер read-only. У production для сценарію, де потрібне лише читання, краще застосувати додаткове обмеження на рівні ОС/контейнера або використовувати сервер без write-tools.

Також заданий filesystem path і MCP roots не слід вважати повною security sandbox. У Claude Code вдалося підтвердити підключення filesystem та його tools, але stderr сервера з інформацією про negotiated roots у доступному UI не відображався. У production реальну межу доступу слід забезпечувати правами ОС або ізольованим runtime.

Persistent `memory` може накопичувати помилкові або небажані дані, які впливатимуть на наступні сесії агента. У цьому навчальному репозиторії memory використовується лише для демонстрації MCP persistence; у production потрібні правила щодо provenance, очищення та допустимих даних у memory.
