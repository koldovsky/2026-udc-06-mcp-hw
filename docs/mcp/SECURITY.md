# Threat model MCP-інтеграцій (Task C)

## 1. Що до чого має доступ

| Сервер | Дані/ресурси, до яких дістає | Секрети | Може писати? | Довіра до автора |
|---|---|---|---|---|
| `filesystem` | Аргумент задає `./app/data`, але реальна область доступу ширша (корінь репозиторію) | немає | **так**  | офіційний (`@modelcontextprotocol/server-filesystem`) |
| `memory` | Немає доступу до диска чи мережі — власний knowledge graph, що існує лише в пам'яті процесу сервера й зникає з його завершенням | немає | так, але лише у власний in-memory граф  | офіційний (`@modelcontextprotocol/server-memory`) |
| `catalog` | `app/data/catalog.json` — лише читання, через `loadCatalog()` з `app/dist/index.js` | немає | ні  | custom |

## 2. Ризики, які я вважаю реальними для цієї конфігурації

- **Prompt injection через дані.** Жоден із трьох серверів не тягне контент ззовні, `memory` не читає нічого зовнішнього. 
- **Занадто широка область доступу.**  `filesystem`-сервер задекларовано на `./app/data`, але фактично (через `roots`/дефолтну поведінку клієнта) агент отримав доступ до кореня репозиторію. Це означає, що агент через цей сервер міг би прочитати (теоретично записати) будь-який файл репозиторію, а не лише `catalog.json`, включно з `.env`, якби він існував і не був у `.gitignore`.
- **Витік секретів.** Жоден із трьох серверів (`filesystem`, `memory`, `catalog`) не потребує токена.  Якщо в майбутньому додати сервер із токеном (Task E, шлях 3), ризик стане реальним і головна точка витоку — випадковий коміт `.env` або хардкод значення прямо в `.mcp.json`.
- **Зміна поведінки сервера після встановлення.** `filesystem` і `memory` запускаються через `npx -y ...` з `@latest` версією — кожен новий запуск `npx` може підтягнути новішу версію пакета з іншою поведінкою чи новим tool без явного рев'ю. Власний сервер (`mcp-server/package.json`) теж використовує дiaпазони, а не точні версії.
- **Дії з побічним ефектом.** Кастомний `catalog`-сервер не має жодного tool із побічним ефектом — усі три tools лише читають (`loadCatalog()` → чисті функції з `app/src/catalog.ts`). `filesystem` додає в хост tools `write_file`, `edit_file`, `move_file`, `create_directory`, які не забороняють агенту змінити файли в межах  області проекту — підтвердження перед викликом залежить від налаштувань хоста.

## 3. Що я зробив, щоб це зменшити

- Для `filesystem` в `.mcp.json` вказано аргумент `./app/data`.
- Власний `mcp-server/`  **read-only**: у коді (`mcp-server/src/server.ts`) зареєстровано лише `registerTool` для `search_inventory`, `check_stock`, `low_stock` і один `registerResource` для `inventory://catalog`.
- Доменна логіка (`searchProducts`, `findBySku`, `lowStock`, `categories`, `inventoryValue`) імпортується з `app/dist/index.js`, бізнес-правила залишаються в одному протестованому місці (`cd app && npm test` — 8 зелених тестів).
- Секрети відсутні: жоден з трьох серверів не потребує токена, `.env` у `.gitignore`.
- Реальну (а не задекларовану) поведінку `filesystem`-сервера щодо scope зафіксовано в `docs/mcp/servers.md`.

## 4. Що лишилось прийнятим ризиком

- Фактична область доступу `filesystem`-сервера ширша за аргумент у `.mcp.json` (корінь репо, а не `./app/data`)
- Версії `filesystem` і `memory` не ідентифіковані (`@latest`)
