# MCP-сервери проєкту (Task A)

**Хост(и), у якому налаштовано:** Claude Code 2.1.231 (macOS 15.6, Node v26.7.0)
**Файли конфігурації:**
- [`.mcp.json`](../../.mcp.json) — самі сервери, project scope, закомічений у git
  (`.gitignore:38-40` прямо просить його комітити)
- [`.claude/settings.json`](../../.claude/settings.json) — deny-rules на
  write-tools. Теж комітиться (`.gitignore:41-42` ігнорує `.claude/*`, але робить
  виняток саме для `settings.json`), тобто обмеження їде разом із репо, а не
  живе лише на одній машині

Підключено **два публічні** сервери (це і є Task A). Вони обрані як контрастна
пара, а не як «два з переліку»: `filesystem` має найширшу можливу поверхню
(14 tools, з них 4 пишуть) і тому потребує справжньої межі; `memory` не має ні
файлової системи, ні мережі взагалі. Різниця між ними — і є урок про scope.

Третім у тому ж `.mcp.json` зареєстрований **власний** сервер `catalog` із
Task B. Він описаний коротко в кінці цього документа, повністю — у
[`mcp-server/README.md`](../../mcp-server/README.md).

**Секрети: жодного в Task A.** Ні `filesystem`, ні `memory`, ні власний `catalog`
токена не потребують. `${ENV_VAR}` у конфізі з'явився пізніше — у Task E разом із
сервером `github`, і значення живе в гітігнорованому `.env`; літеральних значень у
репо немає ніде (`git grep` чистий). Деталі — у
[`task-e-bonus.md`](../task-e-bonus.md).

> **Головний висновок цього документа, одразу і без прикрас:** для `filesystem`
> вдалося обмежити **дії** (запис заблоковано), але **не вдалося обмежити шлях**.
> Аргумент `./app/data` у конфізі — це лише *побажання*: Claude Code передає
> серверу свої MCP roots, і той **заміщує** ним видані директорії. Фактично
> виданий scope — **корінь репозиторію**. Це виміряно, а не припущено, і
> розписано у розділі «Roots» нижче.

Виміряний scope: `/Users/…/2026-udc-06-mcp-hw`. Тобто читання **не** обмежене `app/data`: доступні й `app/src`, і `.git`, і решта репо. Деталі й доказ — у розділі «Roots» |

**Які tools він дав агенту:** сервер реєструє 14 — `read_file`, `read_text_file`,
`read_media_file`, `read_multiple_files`, `list_directory`,
`list_directory_with_sizes`, `directory_tree`, `search_files`, `get_file_info`,
`list_allowed_directories` плюс **`write_file`, `edit_file`, `move_file`,
`create_directory`**.

Останні чотири не вимикаються прапорцем — **у сервера немає read-only режиму.**
Перевірено не по README, а по коду пакета: у `dist/index.js` рівно 4 tools мають
`readOnlyHint: false`, і це саме вони. Тому їх прибрано на рівні хоста: у
`.claude/settings.json` стоїть deny, і **до агента доходять 10 tools, а не 14**.

### Застосована мітигація — deny-rules (і чому саме така)

```json
{ "permissions": { "deny": [
  "mcp__filesystem__write_file",   "mcp__filesystem__edit_file",
  "mcp__filesystem__move_file",    "mcp__filesystem__create_directory" ] } }
```

Це потрібно, бо `app/AGENTS.md` прямо забороняє змінювати
`app/data/catalog.json` — Task D порівнює саме ці числа. Без deny-rule сервер мав
би повне право його перезаписати.

Імена перелічені явно, а не шаблоном `mcp__filesystem__*`: якщо в наступній
версії з'явиться новий write-tool, він **не** буде тихо покритий правилом — це
помітно зламається і змусить перечитати список, замість того щоб створити
ілюзію захисту.

**Доказ, що працює:** у сесії з `--allowedTools mcp__filesystem__write_file`
інструмента просто **немає** в списку доступних — deny прибирає його з поверхні,
а не відмовляє при виклику. `app/data/` після спроби містить тільки
`catalog.json` з незмінним mtime.

**Чесно про силу цієї межі:** це **політика хоста, а не межа ОС**. Правило живе у
файлі, який можна відредагувати, і діє лише там, де його читає Claude Code. Воно
не дає жодних гарантій процесу `node`, який усе ще запущений із правом запису на
весь репозиторій. Порівняння з альтернативою — у розділі про Docker нижче.

**Перевірка, що працює:**

1. `claude mcp list` → `filesystem: npx -y @modelcontextprotocol/server-filesystem@2026.7.10 ./app/data - ✔ Connected`.
2. Реально виданий scope (не з конфіга, а з самого сервера) —
   `list_allowed_directories`:
   ```
   Allowed directories:
   /Users/igor.rakhmanov-external/work/study/ai/modern-dev-with-agentic-ai-ws/2026-udc-06-mcp-hw
   ```
3. Читання цільового файлу: `read_text_file` на `app/data/catalog.json` повертає
   каталог (`KB-1001 Mechanical Keyboard TKL`, …).
4. Читання **поза** `app/data` — на жаль, теж працює: `read_text_file` на
   `AGENTS.md` у корені репо повернув `# AGENTS.md`. Саме це й доводить, що
   рядок «scope» вище описує реальність, а не конфіг.

### Roots — те, через що scope і поїхав

Walkthrough просить подивитися на поведінку roots на власні очі. Тут вона
виявилася не косметичною деталлю, а тим, що визначає фактичний scope.

**Що в коді сервера.** `dist/index.js:574-585`:

```js
allowedDirectories = [...validatedRootDirs];   // повне ЗАМІЩЕННЯ, не об'єднання
```

`getValidRootDirectories()` (`dist/roots-utils.js`) перевіряє лише, що шлях
розбирається, **існує** (`fs.realpath`) і є директорією. **Перевірки вкладеності
в аргументи командного рядка немає.** Плюс окремий обробник
`RootsListChangedNotificationSchema` робить те саме заміщення **у рантаймі** —
тобто scope може змінитися вже після старту.

**Що робить Claude Code.** Він оголошує roots capability, сервер їх запитує
(у логах хоста `Received ListRoots request from server`, а рядка `Client does not
support MCP Roots` немає — він з'являється тільки для клієнта без roots). У
відповідь Claude Code віддає **корінь проєкту**, і сервер його приймає.

Три спостереження, кожне з реальним stderr:

| Клієнт | stderr сервера | Виданий scope |
|---|---|---|
| Ручний проб **без** roots capability | `Client does not support MCP Roots, using allowed directories set from server args: [ '…/app/data' ]` | `…/app/data` ✅ |
| Ручний проб, що віддає корінь репо | `Updated allowed directories from MCP roots: 1 valid directories` | `…/2026-udc-06-mcp-hw` ❌ |
| **Claude Code** | `Received ListRoots request from server` | `…/2026-udc-06-mcp-hw` ❌ |

**Це не вимикається.** У бінарнику Claude Code немає ні прапорця, ні env-змінної
для roots — лише імена схем SDK (`ListRootsRequestSchema`,
`RootsListChangedNotificationSchema`). Не допоможе ні абсолютний шлях замість
відносного (заміщення відбувається незалежно від аргументу), ні винесення даних
у директорію поза репо: scope усе одно став би коренем репо, тільки тепер уже
**без** потрібного каталогу.

**Практичний висновок, і він неприємний:** у парі «Claude Code + цей сервер»
шлях у `.mcp.json` — це **не механізм безпеки, а підказка на випадок, якщо
клієнт roots не підтримує**. Roots — механізм координації (у ревізії специфікації
`2026-07-28` він узагалі позначений як deprecated), але наслідок у нього цілком
безпековий: клієнт, а не ваш конфіг, вирішує, що серверу видно.

### Чого це коштувало: порівняння з Docker-варіантом

Спершу цей сервер був піднятий через Docker із bind mount
`src=…/app/data,dst=/projects/data,ro`. Там scope **тримався** — і тепер видно
чому: host-шляхи з roots не проходили `fs.realpath` **всередині контейнера**,
відкидалися (`Skipping invalid path or inaccessible: …` → `No valid root
directories provided by client`), і аргумент запуску виживав. Запис падав з
`Error: EROFS: read-only file system` — помилкою ядра.

| | Docker + `ro` | npx + deny-rules (обрано) |
|---|---|---|
| Запис заблоковано | `EROFS`, ядро | deny-rule, політика хоста |
| Область читання | `/projects/data` — **втрималася** | корінь репо — **поїхала** |
| Версія коду | образ ~на рік старіший за npm | `2026.7.10`, актуальна |
| Залежності | потрібен Docker; падіння демона вбиває сервер | лише Node |
| Шляхи | `/projects/data/…`, окремий простір | звичайні host-шляхи |

**Чому все одно обрано npx:** актуальний код, відсутність залежності від Docker
(конфіг запускається в будь-кого, а не лише там, де підняте Rancher/Docker
Desktop) і відсутність зв'язку живучості сервера з демоном контейнерів — під час
роботи над завданням демон Docker справді впав і забрав сервер із собою.
Ціна — та сама, що в таблиці: **обмежені дії, необмежений шлях читання.**

Для цього конкретного репо ризик приймається свідомо: усі дані синтетичні,
секретів у репо немає (перевірено `git grep`), а `.env` не існує. У репозиторії
з реальними даними такий обмін був би неприйнятним — там правильна відповідь
саме контейнер, і причина тепер задокументована, а не вгадана.

### Як перевірити вручну

Найважливіша перевірка — **виміряти виданий scope, а не прочитати його з
конфіга**. Через хост:

```bash
claude mcp list      # → filesystem: … ✔ Connected
claude -p "Call the filesystem MCP tool list_allowed_directories and print its exact raw output." \
  --allowedTools "mcp__filesystem__list_allowed_directories"
```

Показати сам механізм roots можна розмовою з сервером напряму по stdio — тоді
видно і сирі JSON-RPC відповіді, і stderr, який хост інакше ховає у свої логи.
Запускати з кореня репо. Різниця між двома пробами — рівно в одному полі
`capabilities`:

```bash
PKG=@modelcontextprotocol/server-filesystem@2026.7.10

# A. Клієнт БЕЗ roots → виживає аргумент ./app/data
{ echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"0"}}}'
  sleep 1
  echo '{"jsonrpc":"2.0","method":"notifications/initialized"}'
  sleep 1
  echo '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"list_allowed_directories","arguments":{}}}'
  sleep 2
} | npx -y "$PKG" ./app/data 2>&1 >/dev/null | grep -v "npm warn"
#   → Client does not support MCP Roots, using allowed directories set from server args: [ '…/app/data' ]

# B. Клієнт З roots, що віддає корінь репо → аргумент заміщено
{ echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{"roots":{"listChanged":true}},"clientInfo":{"name":"probe","version":"0"}}}'
  sleep 1
  echo '{"jsonrpc":"2.0","method":"notifications/initialized"}'
  sleep 1
  echo "{\"jsonrpc\":\"2.0\",\"id\":0,\"result\":{\"roots\":[{\"uri\":\"file://$PWD\",\"name\":\"repo\"}]}}"
  sleep 2
} | npx -y "$PKG" ./app/data 2>&1 >/dev/null | grep -v "npm warn"
#   → Updated allowed directories from MCP roots: 1 valid directories
```

`sleep` тут не для краси: без них pipe закривається раніше, ніж сервер завершить
handshake. Ідентифікатор відповіді на серверний запит `roots/list` у пробі B
вгадується (`id: 0`) — сервер надсилає запит сам, і в такому «сліпому» скрипті
його id не видно.

Логи stderr, які пише сам хост, лежать тут:
`~/Library/Caches/claude-cli-nodejs/<slug-репо>/mcp-logs-filesystem/*.jsonl`.
Врахуйте, що хост зберігає **не весь** stderr сервера: у наших запусках туди
потрапив лише стартовий рядок, тому рішення про roots доводилося міряти
викликом tool, а не читанням логу.

Повний опис — у [`mcp-server/README.md`](../../mcp-server/README.md); тут лише

ground truth із `app/dist`. Ресурс хост бачить (`"hasResources":true` у лозі),
але дістається він нерівно — деталі й таблиця спроб у README сервера; для Task D
з цього зроблено висновок, що покладатися треба на tools.

**Головне для цього документа:** із трьох серверів у конфізі шлях реально
тримається **тільки** у цього — і не завдяки конфігу, а тому, що шлях узагалі
не є параметром. Найнадійніший спосіб звузити область доступу MCP-сервера —
не передавати йому шлях, а зашити його в код, який ви контролюєте.

| **Область доступу (scope)** | GitHub API у межах прав токена: read-only, публічні репозиторії, без дозволів на акаунт. **26 tools замість 44** — прапорець `--read-only` не реєструє 18 write-tools (виміряно). Тобто межу тут тримає **сам сервер**, а не політика хоста, як у `filesystem` |
| **Секрети** | Один токен — **тільки** через `${GITHUB_PERSONAL_ACCESS_TOKEN}`; значення в `.env` (`.gitignore:15`), у репо — `.env.example` |
| **Версія** | **Запінена за digest** образу, не за тегом `latest` |

Дві незручні знахідки, які варто мати перед очима: (1) якщо змінна не задана,
Claude Code передає далі текст плейсхолдера, сервер стартує на не-секреті й
показується як `✔ Connected` — статус не є перевіркою секрету; (2) занадто старий
запінений образ під'єднується, але його payload не проходить валідацію сучасного
клієнта, і tools не доходять до моделі. Обидві перевірені й розписані в
`task-e-bonus.md`.

## Що НЕ підключали і чому

Уточнення, важливе для чесності цієї таблиці: «не підключали» тут означає **не
вносили в project-конфіг, який їде в PR**. Частина цих можливостей усе одно
присутня в сесіях через user-scope конфіг (`~/.claude.json`) — див.
[`SECURITY.md`](./SECURITY.md), де описана вся поверхня сесії, а не лише вміст
`.mcp.json`.

| Сервер | Чому не взяли |
|---|---|
| `git` (uvx) | Має write-tools (`git_add`, `git_commit`, `git_create_branch`), а git у Claude Code вже доступний через Bash. Чистий приріст поверхні без приросту можливостей |
| `fetch` (uvx) | Fetch довільного URL — найгостріший вектор prompt injection: у контекст агента потрапляє зовнішній текст, який може бути адресований самому агенту. У цьому репо ним нічого не закривається. **Зауваження, знайдене в Task C:** user-scope сервер `searxng` має tool `get_website(url)`, який робить фактично те саме — тобто відмова від `fetch` у project-конфізі не означає, що цієї можливості в сесії немає (див. [`SECURITY.md`](./SECURITY.md)) |
| `playwright` | **Немає застосування:** `app/` — звичайна бібліотека без UI, сервер Task B — stdio, Task C і D — документи. Драйвити нема чого. А ціна висока: серед tools є `browser_run_code_unsafe`, який у власному описі названий *«RCE-equivalent»*, і `browser_navigate`, що дістає `localhost` |

той випадок, коли walkthrough дозволяє «немає uv — беріть npx-пару».

## Область доступу — головне

Найважливіший рядок у обох блоках вище — **scope**. У цьому конфізі він тримається
на трьох рівнях, і — головне — **один із трьох не втримався**. Саме це і є
найцінніше, що дала Task A.

1. **Шлях — не втримався.** Задано `./app/data`, фактично видано корінь
   репозиторію. Не тому, що конфіг написано неправильно, а тому, що клієнт
   передає roots, а сервер ними **заміщує** видані директорії. Виміряно через
   `list_allowed_directories` і підтверджено успішним читанням `AGENTS.md` поза
   `app/data`. **Урок: шлях у конфізі MCP-сервера — це не контроль доступу.** Це
   значення за замовчуванням, яке клієнт має право перезаписати.
2. **Дії — втрималися.** Сервер не має read-only режиму (4 tools із
   `readOnlyHint: false` у коді), тому 4 write-tools прибрано deny-rules у
   `.claude/settings.json`. До агента доходить 10 tools із 14, і `write_file`
   недоступний навіть за явного `--allowedTools`. Це справжня, перевірена
   мітигація — але **політика хоста, а не межа ОС**: файл можна відредагувати, і
   процес `node` під нею все ще має право запису на весь репозиторій.
3. **Радіус ураження — врахований.** У `memory` є чотири delete-tools, і це
   нормально там, де у `filesystem` було ні: вони руйнують лише власний граф
   сервера. Один і той самий дієслівний набір («видаляє») означає різний ризик
   залежно від того, до чого він дотягується.

Тобто твердження «сервер файлової системи, якому віддали `/`, — це дірка»
потребує уточнення, яке видно тільки на практиці: **віддати `/` можна не тільки
руками в конфізі.** Можна написати вузький шлях, бути впевненим у ньому — і
отримати широкий, бо його переписав хост. Перевіряти треба не те, що ви
**задали**, а те, що сервер **віддає** у `list_allowed_directories`.

Єдина конфігурація з цих двох перевірених, де шлях реально втримався, — сервер у
контейнері, куди змонтовано рівно одну директорію: там roots із host-шляхами
фізично не резолвляться. Ми обрали npx свідомо, з відкритими очима на цей обмін
(див. таблицю порівняння вище), і для репо з синтетичними даними він приймається.
Для репо з реальними — ні.

І третій варіант, який Task B показала вже практично: **не передавати шлях
взагалі.** У власного сервера `catalog` область доступу — один файл, і вона
тримається без жодного контейнера й без жодного deny-rule, бо шлях не є ні
аргументом, ні предметом переговорів із клієнтом — він обчислюється в коді, який
ми контролюємо. Порядок надійності за цими трьома вимірами вийшов такий: **код,
що не приймає шлях** > **межа ОС/контейнера** > **політика хоста** > **аргумент
у конфізі** (останній не є контролем узагалі).
