## Сервер 1 — filesystem (`@modelcontextprotocol/server-filesystem`)

| | |
|---|---|
| **Навіщо** | Дає агенту читати/писати файли самого репозиторію (код, `app/data/catalog.json`, доки) без ручного копіпасту вмісту файлів у чат |
| **Транспорт** | stdio |
| **Як запускається** | `npx -y @modelcontextprotocol/server-filesystem /Users/liudmyla.minenkova/Documents/Raif_AI/2026-udc-06-mcp-hw` |
| **Область доступу (scope)** | Один аргумент — корінь цього репозиторію (`2026-udc-06-mcp-hw`), а не домашня тека і не `/`. Усередині нього сервер сам далі обмежує кожен виклик перевіркою `path outside allowed directories` (перевірено нижче на `/etc/hosts`). Корінь репо, а не вужчий `app/data`, обраний свідомо: у Task A/B агенту треба читати ще й `app/src/*.ts`, `docs/*`, `app/AGENTS.md` — звузити до `app/data` означало б, що агент не зможе прочитати власний код каталогу |
| **Секрети** | Немає — токен не потрібен |
| **Версія** | Плаваюча (`npx -y ...` без пінованої версії → на момент перевірки підтягнулась `2026.7.10`). Прийнятно для локального dev-хука на короткій домашці; для команди/CI варто було б запінити |

**Які tools він дав агенту:** `read_file` (deprecated, лишений для сумісності), `read_text_file`, `read_media_file`, `read_multiple_files`, `write_file`, `edit_file`, `create_directory`, `list_directory`, `list_directory_with_sizes`, `directory_tree`, `move_file`, `search_files`, `get_file_info`, `list_allowed_directories` — повний список підтверджено викликом `tools/list` напряму по stdio (без хоста).

**Перевірка, що працює:**
- `tools/call list_directory` з `path=.../app/data` → відповідь `[FILE] catalog.json` — сервер бачить файли репозиторію.
- `tools/call read_text_file` з `path=/etc/hosts` (шлях поза дозволеним коренем) → `isError: true`,
  `"Access denied - path outside allowed directories: /etc/hosts not in /Users/liudmyla.minenkova/Documents/Raif_AI/2026-udc-06-mcp-hw"`.
  Це і є доказ, що scope справді працює, а не просто заявлений в конфізі.
- У stderr сервера при старті видно:
  `Client does not support MCP Roots, using allowed directories set from server args: ['.../2026-udc-06-mcp-hw']` —
  саме той нюанс з `walkthrough.md`: клієнт (перевірка робилась напряму, без `roots`-хендшейка хоста) не підтримує `roots`,
  тому реальний скоуп бере аргумент з конфіга, а не координацію від хоста. Тобто в цьому підключенні межа доступу — це
  буквально шлях, переданий у `.mcp.json`.

## Сервер 2 — memory (`@modelcontextprotocol/server-memory`)

| | |
|---|---|
| **Навіщо** | Дає агенту зберігати нотатки/сутності між репліками одного чату (knowledge graph) — зручно тримати проміжні висновки по Task A–E, не повторюючи їх у кожному промпті |
| **Транспорт** | stdio |
| **Як запускається** | `npx -y @modelcontextprotocol/server-memory` |
| **Область доступу (scope)** | Немає доступу до файлової системи репозиторію взагалі — працює з окремим in-memory graph, який персистить у `memory.jsonl` **всередині власного пакета** (`~/.npm/_npx/<hash>/node_modules/@modelcontextprotocol/server-memory/dist/memory.jsonl`), а не в цьому репо. Перевірено: одразу після старту `read_graph` повернув сутність `User` / "Favorite color is blue", яка лишилась там від попереднього, зовсім не пов'язаного використання цього ж npx-пакета на цій машині. Тобто scope тут — не шлях, а те, що сервер не бачить репозиторій узагалі; але дані між непов'язаними проєктами, які запускають цей самий npx-пакет, можуть змішуватись, якщо не задати `MEMORY_FILE_PATH`. Для цієї домашки ризик прийнятний (нема секретних даних), але для реального проєкту варто явно задати `MEMORY_FILE_PATH` в межах репо |
| **Секрети** | Немає — токен не потрібен |
| **Версія** | Плаваюча (`npx -y ...`, підтягнулась `2026.7.4`) — так само прийнятно для домашки |

**Які tools він дав агенту:** `create_entities`, `create_relations`, `add_observations`, `delete_entities`, `delete_observations`, `delete_relations`, `read_graph`, `search_nodes`, `open_nodes` — підтверджено викликом `tools/list`.

**Перевірка, що працює:** викликано послідовність `create_entities` (додано тестову сутність `ws06-test` з observation "перевірка servers.md") → `read_graph` (сутність з'явилась у графі, поряд зі старим `User`) → `delete_entities` (`{"success": true, "message": "Entities deleted successfully"}`) — прибрано тестову сутність, щоб не залишати сміття в чужому спільному файлі пакета.

## Що НЕ підключали і чому

Розглядали **git** та **fetch** (обидва рекомендовані у `walkthrough.md`, запускаються через `uvx`). Свідомо не додали:
`git`-сервер дає доступ на рівні репозиторію до історії й гілок — для Task A–D він не потрібен (файлового доступу
через `filesystem` достатньо), а `fetch` — це `openWorldHint: true` за своєю суттю: сервер, що ходить у довільний
інтернет і затягує чужий текст просто в контекст агента. Для домашки без задачі "витягни щось з вебу" це зайва
поверхня атаки (саме той сценарій "текст, адресований агенту" з `docs/mcp/SECURITY.md`) без відповідної користі —
тому обмежились двома локальними, детермінованими серверами без мережевого виходу.

## Область доступу — головне

Найважливіший рядок у кожному блоці вище — **scope**. Сервер файлової системи,
якому віддали `/` або весь домашній каталог, — це не «зручно налаштовано», це
дірка. Для filesystem-сервера в цьому репо явно передано лише корінь
`2026-udc-06-mcp-hw` (не `~`, не `/`), і це перевірено практично: спроба
прочитати `/etc/hosts` відхилена сервером з помилкою `Access denied`. Для
memory-сервера доступу до файлової системи проєкту немає взагалі — його
"область доступу" це окремий JSON-граф поза репозиторієм, і про це явно
написано вище разом із побаченим побічним ефектом (спільний файл між
проєктами).
