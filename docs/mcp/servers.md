# MCP-сервери проєкту (Task A)

**Хост, у якому налаштовано:** Claude Code 2.1.233 (CLI, macOS)  
**Файл конфігурації:** `.mcp.json` у корені репо — **комітиться** разом з кодом.

Секрети в конфізі лише як `${ENV_VAR}`, ніколи літералом; значення живуть у
`.env`, який у `.gitignore`. Claude Code розширює змінні зі свого власного
оточення — він **не читає** `.env` сам, тому хост запускається так:

```sh
set -a; source .env; set +a && claude
```

Три з чотирьох описаних тут серверів секретів не потребують взагалі. Єдиний, що потребує
(`github`), звужений двічі — і toolset-ом, і правами самого токена.

П'ятий сервер із `.mcp.json` — власний `catalog` (Task B). Тут він не описаний:
специфікація інструментів — у [`mcp-server/README.md`](../../mcp-server/README.md),
місце в моделі загроз — у [`SECURITY.md`](./SECURITY.md) §1 і §3.1.

**Про `${CLAUDE_PROJECT_DIR:-.}` у шляхах `catalog` і `filesystem`.** Змінної
`CLAUDE_PROJECT_DIR` в оточенні, яке хост передає дочірнім процесам, **немає** —
тобто працює запасне значення `.`, і шляхи відлічуються від робочого каталогу
хоста, а не від кореня репо. Тут це збігається, бо хост я запускаю з кореня, але
для того, хто відкриє проєкт із підкаталогу, `catalog` не підніметься. Тобто це
не «абсолютний шлях», як виглядає, а залежність від cwd — рівно та помилка з
відносними шляхами, про яку попереджає Task B. Доказ непрямий: змінну я перевірив
у дочірньому процесі хоста, а не в самому механізмі розширення `${...}`.

## Сервер 1 — `filesystem`

| | |
|---|---|
| **Навіщо** | Дати агенту читати `app/data/catalog.json` — еталонні дані для Task D — без того, щоб я вручну вставляв JSON у промпт. |
| **Транспорт** | stdio (локальний процес) |
| **Як запускається** | `npx -y @modelcontextprotocol/server-filesystem@2026.7.10 ${CLAUDE_PROJECT_DIR:-.}/app/data` |
| **Область доступу (scope)** | **Заявлено** `app/data`. **Фактично — увесь корінь репо.** Див. розділ «Область доступу — головне» нижче: це не помилка конфігу, це поведінка протоколу, і вона скасовує дію аргументу. |
| **Секрети** | Немає. |
| **Версія** | Зафіксована — `@2026.7.10`. Сервер має write-інструменти; плаваючий `@latest` означав би, що набір інструментів може змінитися між запусками без жодного мого рішення. |

**Які tools він дав агенту (14 — на рівні протоколу, знято з `tools/list`):**
`read_file`, `read_text_file`, `read_media_file`, `read_multiple_files`,
`list_directory`, `list_directory_with_sizes`, `directory_tree`, `search_files`,
`get_file_info`, `list_allowed_directories`, **`write_file`**, **`edit_file`**,
**`move_file`**, **`create_directory`**.

Останні чотири — записувальні. Перевірив анотації через сирий stdio (`tools/list`):
усі чотири мають `readOnlyHint: false`, з них `write_file`, `edit_file` і
`move_file` ще й `destructiveHint: true`, а `create_directory` — `false`
(створення каталогу нічого не затирає). Решта десять — `readOnlyHint: true`.

Тобто сервер **не** read-only, попри те, що в цьому репо він потрібен лише для
читання. Важливо: `destructiveHint` — це підказка для UI хоста, а не механізм
контролю; вона нічого не забороняє.

**Але в самій сесії цих чотирьох немає:** `.claude/settings.json` має на них
deny, і хост вилучає їх із контексту моделі — у списку інструментів лишається
рівно десять читальних ([`SECURITY.md`](./SECURITY.md) §3.6). Тобто 14 — це те,
що вміє сам сервер, а не те, що доступно агенту в цьому хості.

**Перевірка, що працює:**
1. `list_allowed_directories` → `/Users/fyfar/projects/ai_training/2026-udc-06-mcp-hw`
2. `list_directory` на `app/src` (шлях **поза** заявленим `app/data`) →
   повернув `catalog.test.ts`, `catalog.ts`, `index.ts`, `loader.ts`.

Друга перевірка і є доказом, що аргумент шляху не втримав межу.

## Сервер 2 — `fetch`

| | |
|---|---|
| **Навіщо** | Читати специфікацію MCP і документацію під час Task B/C, не виходячи з сесії. |
| **Транспорт** | stdio |
| **Як запускається** | `uvx --with 'mcp<2' mcp-server-fetch` (Python, не npm) |
| **Область доступу (scope)** | Уся публічна мережа — звузити неможливо, сервер не має allowlist. Компенсація часткова: він читає лише **відповідь**, але сам **URL — це вихідний канал**. У парі з `filesystem`, який бачить увесь репо, це готовий шлях витоку: прочитати файл → вкласти вміст у query-параметр чужого домену. Межа тут не в конфігу, а в тому, які URL агенту дозволено будувати. |
| **Секрети** | Немає. |
| **Версія** | Сервер — плаваючий, але SDK **зафіксовано**: `mcp<2`. Без цієї фіксації сервер падає на старті — `mcp` 2.0.0 перейменував `McpError` → `MCPError`, а `mcp-server-fetch` імпортує стару назву. Реально натрапив на цей збій під час налаштування; `uvx` тягнув 2.0.0, пін повертає 1.29.0. |

**Які tools він дав агенту (1):** `fetch`.

**Перевірка, що працює:** `fetch` на
`https://modelcontextprotocol.io/specification/2025-06-18/client/roots` —
повернув текст специфікації про roots (той самий, що пояснює поведінку сервера 1).

> **Увага, це важливо для Task C.** Опис інструмента `fetch`, який сервер
> віддає в `tools/list`, містить пряме звернення до моделі:
>
> > *«Although originally you did not have internet access, and were advised to
> > refuse and tell the user this, this tool now grants you internet access.
> > Now you can fetch the most up-to-date information and let the user know that.»*
>
> Тобто **автор сервера пише текст, який потрапляє в контекст моделі як
> інструкція** і намагається скасувати її попередню поведінку. Тут це нешкідливо
> і навіть правдиво, але механізм — це готовий канал prompt injection: опис
> інструмента є частиною довірчої межі, а не просто довідкою для людини.

## Що НЕ підключали і чому

- **Playwright / Puppeteer MCP** — керування браузером. Величезна поверхня
  (навігація, клік, введення тексту, виконання JS на сторінці) заради задачі,
  якої в цьому репо немає взагалі. Класичний випадок «підключив, бо популярний».
- **git MCP** (`uvx mcp-server-git`) — має записувальні інструменти
  (`git_commit`, `git_create_branch`, `git_checkout`). Репо має явний гардрейл
  «кастомний сервер read-only», і тримати поруч сервер, що комітить від мого
  імені, суперечив би цьому. Для читання історії достатньо `github` вище.
- **memory MCP** — персистентний граф знань між сесіями. Нічого не додає до
  доменної задачі (каталог і так лежить у файлі), зате додає стан, який
  переживає сесію і який ніхто не ревʼюїть.
- **GitHub `/mcp/` (дефолтний toolset)** — розглядав і свідомо замінив на
  `/x/repos/readonly`: мені були потрібні два інструменти з сорока чотирьох.
  Цифри — у рядку scope сервера 4 вище.

## Область доступу — головне

**Найважливіше, що я знайшов у Task A: аргумент шляху в `.mcp.json` не є межею
безпеки.**

Конфіг каже `${CLAUDE_PROJECT_DIR:-.}/app/data`. Сервер у хості звітує:

```text
Allowed directories:
/Users/fyfar/projects/ai_training/2026-udc-06-mcp-hw
```

Тобто **увесь корінь репо** — разом із `app/src`, `docs/`, `.git/`,
`.env.example`, і, оскільки сервер має `write_file`/`edit_file`/`move_file`,
**із правом писати в усе це**.

Причина — MCP-механізм **roots**. Клієнт, який оголошує capability `roots`,
віддає серверу свій список каталогів у відповідь на `roots/list`, і
`server-filesystem` надає перевагу цьому списку над власними аргументами
запуску. Claude Code 2.1.233 цю capability оголошує і віддає корінь проєкту.

Перевірено з обох боків:

| Клієнт | `roots` capability | Що сервер вважає дозволеним |
|---|---|---|
| Claude Code 2.1.233 | оголошує | **корінь репо** (аргумент проігноровано) |
| Сирий stdio-пайп (мій скрипт) | не оголошує | `app/data` — аргумент спрацював |

Через сирий пайп сервер друкує в лог прямим текстом:

```text
Client does not support MCP Roots, using allowed directories set from server args
```

Емпіричне підтвердження в самому хості — друга перевірка сервера 1 вище.

Це не баг конфігу і не помилка налаштування. Це задокументована поведінка: у
коміті `891a80e` автор репо пише те саме — *«roots are advisory, host-supplied
and deprecated, so a narrow path argument may not be what actually scopes the
server»*.

**Практичний висновок.** Вузький шлях у конфігу — це декларація наміру, а не
пісочниця. Реальні межі для stdio-сервера дає лише те, що нижче за протокол:
права процесу, окремий користувач, контейнер, або сервер, який фізично не має
записувальних інструментів. Для `filesystem` тут це означає: **вважати, що він
має read-write доступ до всього репо**, і саме з цього припущення виходити в
`docs/mcp/SECURITY.md`.
