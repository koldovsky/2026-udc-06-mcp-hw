# MCP-сервери проєкту (Task A)

**Хост:** Claude Code (Windows 10, Node v24.16.0)
**Конфіг:** `.mcp.json` (корінь репо) + `.claude/settings.json` (права хоста) —
обидва закомічені.

Два npx-сервери, обидва **без токенів**: `filesystem` і `memory`. `uvx`-серверів
(`git`, `fetch`) свідомо не брали — див. «Що НЕ підключали».

> «По stdio» = прямий JSON-RPC виклик сервера власним клієнтом. «У хості» =
> те саме в Claude Code. **Результати різні** — це і є головний висновок Task A.

---

## Головне: «scope» — це три різні речі

| Рівень | Хто **вирішує** | Хто **виконує** |
|---|---|---|
| 1. Які tools існують | сервер (`tools/list`) | сервер |
| 2. Де tool може читати | **хост** — відповідь на `roots/list` | **сервер** — звіряє шлях |
| 3. Який tool можна викликати | **хост** — `allow`/`deny` у `.claude/settings.json` | **хост** — tool зникає зі списку, виклик неможливий |

Аргумент `./app/data` у `.mcp.json` виглядає як рівень 2, але в Claude Code
туди не потрапляє: межу задає хост. Виконує перевірку все одно сервер.
Повернути аргументу силу вдалось лише тим, що рівень 2 перехопили ззовні —
проксі, який не віддає серверу `roots` (див. «Як це закрито»).

## Сервер 1 — filesystem (`@modelcontextprotocol/server-filesystem`)

| | |
|---|---|
| **Навіщо** | Дати агентові прочитати `app/data/catalog.json` — ground truth для Task D. Базовий рівень A/B: без власного MCP-сервера агент лише читає сирий JSON і рахує сам. |
| **Транспорт** | stdio |
| **Запуск** | Не напряму, а **через проксі**: `node ./scripts/fs-proxy.mjs --allow ./app/data/catalog.json -- ./node_modules/@modelcontextprotocol/server-filesystem/dist/index.js ./app/data` |
| **Scope** | **Один файл** — `app/data/catalog.json`. Два незалежні рівні: проксі звіряє кожен шлях зі своїм allowlist, а сам сервер обмежений `./app/data`, бо проксі **не віддає йому `roots`** (див. «Хто насправді задає scope»). |
| **Права** | Read-only силами хоста **і** проксі: назовні видно 2 tools (`read_text_file`, `list_allowed_directories`), решту проксі не пропускає й не показує в `tools/list`. |
| **Секрети** | Немає. |
| **Версія** | `2026.7.10` у `devDependencies` кореня, тож пін тримає ще й `package-lock.json` — не лише тег, а хеш вмісту. Плаваючий `@latest` виконав би будь-який реліз upstream без рев'ю. |

**Tools (14):** `read_file`, `read_text_file`, `read_media_file`,
`read_multiple_files`, `write_file`, `edit_file`, `create_directory`,
`list_directory`, `list_directory_with_sizes`, `directory_tree`, `move_file`,
`search_files`, `get_file_info`, `list_allowed_directories`.
У хості дозволені **2** (`read_text_file`, `list_allowed_directories`), решта
**12** — поіменно в `deny`. Усі 14 названі явно: tool, якого немає ні в
`allow`, ні в `deny`, не заблокований — він просто питає дозволу.

### Розбір рядка запуску

```
node ./scripts/fs-proxy.mjs --allow ./app/data/catalog.json -- ./node_modules/@modelcontextprotocol/server-filesystem/dist/index.js ./app/data
     └────── рівень 1 ─────┴───── його опції ─────────────┘    └───────────────────── рівень 2 ─────────────────────────────┴── його опції ──┘
```

**Два запуски, склеєні в один рядок**, розрізані по `--`. Шляхи — відносно
кореня репо.

| Аргумент | Чий | Що робить |
|---|---|---|
| `./scripts/fs-proxy.mjs` | `node` | Запускається **це**, а не сервер: хост говорить лише з проксі |
| `--allow ./app/data/catalog.json` | проксі | Allowlist — **один файл**. Повторюваний. На старті канонізується через `realpathSync.native`; нерезолвний шлях або порожній allowlist = вихід з кодом 2 (не «дозволено все») |
| `--` | проксі | Роздільник. Обовʼязковий: без нього проксі не вгадує, де чиї прапорці, а виходить з кодом 2 |
| `…/server-filesystem/dist/index.js` | проксі | Команда дитини. Розширення `.js` вмикає гілку `spawn(process.execPath, …)` — **без шела** (`fs-proxy.mjs:139`); `npx` на Windows тягнув би `.cmd`-шим і `DEP0190` |
| `./app/data` | **дитини** | Аргумент самого сервера — його власний каталог-scope |

Останній рядок — другий, незалежний рівень:

| Рівень | Межа | Хто перевіряє |
|---|---|---|
| проксі | `app/data/catalog.json` (**один файл**) | allowlist + фільтр `tools/list` |
| сервер | `app/data/` (**каталог**) | власна перевірка всередині пакета |

Діє вужчий — сьогодні це лише `catalog.json`. Зовнішній рівень потрібен на
випадок помилки в проксі: межа просідає до `app/data`, а не до всього репо. І
він реальний лише завдяки вирізанню `roots`, інакше хост перезаписав би
`./app/data` коренем репо (див. «Як це закрито»).

> Тому ж тест запускає дитину з **коренем репо** (`fs-proxy.test.mjs:4-7`):
> звужена до `app/data`, вона відмовляла б `.env` самотужки — і тест не доводив
> би нічого про проксі.

### Чому scope — каталог, а не файл

Сервер приймає лише каталоги:

```
$ npx -y @modelcontextprotocol/server-filesystem ".../app/data/catalog.json"
Warning: C:\...\app\data\catalog.json is not a directory, skipping
Error: None of the specified directories are accessible
```

Тому найвужче, що можна вказати аргументом, — каталог `app/data`. Стосується
лише fallback-гілки: у Claude Code аргумент не діє взагалі.

### Чому read-only — на рівні хоста

Прапорця read-only для npx-запуску немає (є лише в Docker через `ro`-mount);
`readOnlyHint` — підказка моделі, не заборона. Перевірка по stdio (клієнт
**без** roots, тому scope справді був `./app/data`):

| Виклик | Результат |
|---|---|
| `read_text_file("catalog.json")` | ✅ прочитав |
| `read_text_file("../src/catalog.ts")` | ⛔ `Access denied - path outside allowed directories` |
| `write_file("../../write-probe.tmp")` | ⛔ те саме |
| `write_file("write-probe.tmp")` | ⚠️ **`Successfully wrote`** — усередині scope сервер пише |

(Пробний файл видалено.) Межа тримається, але **всередині межі сервер має
повний запис**. Тому заборона живе рівнем вище:

```json
{
  "permissions": {
    "allow": [
      "mcp__filesystem__read_text_file",
      "mcp__filesystem__list_directory",
      "mcp__filesystem__list_allowed_directories"
    ],
    "deny": [
      "mcp__filesystem__write_file",
      "mcp__filesystem__edit_file",
      "mcp__filesystem__create_directory",
      "mcp__filesystem__move_file",
      "mcp__filesystem__read_file",
      "mcp__filesystem__read_media_file",
      "mcp__filesystem__read_multiple_files",
      "mcp__filesystem__list_directory_with_sizes",
      "mcp__filesystem__directory_tree",
      "mcp__filesystem__search_files",
      "mcp__filesystem__get_file_info"
    ]
  }
}
```

(Наведено лише правила для `filesystem`; у файлі є ще правила для `memory` —
див. нижче.)

**Чому allow звужено до трьох.** Спершу дозволених було 9 читальних. Але якщо
межа — корінь репо, а не `app/data`, то tools-розвідники (`search_files`,
`directory_tree`, `read_multiple_files`, `get_file_info`) сканують уже все
дерево. Для Task D треба `read_text_file` і `list_directory`;
`list_allowed_directories` лишили — він не читає даних, зате дозволяє
перевірити межу. Решта 11 — **поіменно** в `deny`: «не в allow» означає лише
запит підтвердження, а не заборону. Серед них `read_media_file`, який повертає
base64 будь-якого файлу зі scope.

**Чому не можна просто заборонити `.env`.** Правила прав матчаться за **іменем**
tool'а (вайлдкарди на кшталт `mcp__filesystem__*` є), а не за аргументом —
форми `mcp__filesystem__read_text_file(./.env)` не існує. `Read(./.env)` у
`deny` закриє вбудований `Read`, але не MCP-канал: інший tool — інше правило.
Це рівень 2, а його задає хост. Звуження allow прибирає **масову** розвідку
(рекурсивний `directory_tree`, пошук за вмістом `search_files`), але `.env`
лишається і видимим, і читаним: `list_directory(".")` показує його в корені —
див. таблицю нижче — а `read_text_file(".env")` прочитає напряму. Сьогодні там
один ключ, `MCP_MEMORY_FILE` (машинозалежний шлях), тож шкоди немає; але
механізму, який закрив би реальний секрет, у конфізі немає.

Це рівень 3 — єдиний, де конфіг цього репо реально щось тримає. Причому
`deny` не блокує виклик, а **прибирає tool зі списку взагалі**: після
звуження allow шість заборонених tools зникли з доступних тієї ж миті, без
перезапуску — модель їх більше не бачить.

### Хто насправді задає scope

Власний stdio-клієнт дав рядок, про який попереджає walkthrough:

```
Client does not support MCP Roots, using allowed directories set from server args:
[ 'C:\Users\Admin\IdeaProjects\2026-udc-06-mcp-hw\app\data' ]
```

Звідси напрошувалось «аргумент працює» — і це **невірно для Claude Code**.
Рядок означає буквально те, що написано: probe-клієнт roots не підтримував,
хост — підтримує.

Логи MCP пишуться завжди, незалежно від `--debug` (`~/.claude/debug/` існує
лише при `--debug`):

```
%LOCALAPPDATA%\claude-cli-nodejs\Cache\<project-slug>\mcp-logs-filesystem\*.jsonl
```

```
{"error":"Server stderr: Secure MCP Filesystem Server running on stdio\n"}
{"debug":"Received ListRoots request from server"}
```

Сервер попросив `roots/list`, хост відповів. Рядка `Client does not support
MCP Roots` немає в **жодному** лозі (0 збігів по всьому кешу).

> `"error"` у першому рядку — це назва **потоку**, а не рівень серйозності. У
> stdio-транспорті stdout зайнятий JSON-RPC, тому будь-який людський текст
> сервер мусить писати в stderr, а Claude Code кладе весь цей потік під ключ
> `error`. Тут це банер успішного старту. Перевірка: усі 25 записів
> `Server stderr:` у кеші мають ключ `error` — серед них і `npm warn
> deprecated glob@10.5.0`. Справжні помилки йдуть під тим самим ключем, але
> **без** префікса `Server stderr:` (`Access denied…`, `Connection failed…`) —
> саме префікс і відрізняє одне від одного.

**Що з цього вийшло — виміряно в хості:**

| Виклик | Результат |
|---|---|
| `list_allowed_directories()` | `C:\...\2026-udc-06-mcp-hw` — **корінь репо, не `app/data`** |
| `read_text_file(<repo>\CLAUDE.md)` | ✅ прочитав — поза `app/data` |
| `read_text_file(C:\Users\Admin\.claude\settings.json)` | ⛔ `Access denied … not in C:\...\2026-udc-06-mcp-hw` |
| `list_directory(".")` | увесь корінь: `.env`, `.git`, `.claude`, `app`, `docs`, … |

По stdio ті самі виклики давали `C:\...\app\data` і `[FILE] catalog.json`. Один
сервер, той самий `.mcp.json`, різні клієнти — різна межа.

Усі чотири виклики лишились в `allow` і після звуження, тож таблиця
відтворювалась як є. Звуження прибрало розвідку, а не видимість кореня —
корінь закрив уже проксі, див. «Як це закрито» і таблицю після рестарту.

**Але перевіряє шлях усе одно сервер** — текст помилки з коду пакета
(`dist/lib.js:67`), і порядок у лозі це підтверджує:

```
{"debug":"Calling MCP tool: read_text_file"}
{"error":"Access denied - path outside allowed directories: …"}
```

Якби блокував хост, першого рядка не було б.

### Як це закрито

Аргумент `./app/data` став справжньою межею — не тому, що хост передумав, а
тому, що між хостом і сервером тепер стоїть `scripts/fs-proxy.mjs`, який
**вирізає `roots` із capabilities клієнта** в повідомленні `initialize`. Сервер
бачить клієнта без підтримки roots і робить те, що робив у контрольній пробі
вище — бере scope з власних args:

```
fs-proxy: withheld roots capability; child uses its own args
Client does not support MCP Roots, using allowed directories set from server args: [ '…\app\data' ]
```

`list_allowed_directories()` після цього повертає `…\app\data`, а не корінь
репо. Поверх цього проксі ще й звіряє кожен шлях зі своїм allowlist з одного
файлу, тож `.env`, `.git/` і `.claude/` недосяжні навіть у межах `app/data`.
Розбір самого проксі, включно з тим, чому такий підхід слабший за сервер без
параметра-шляху — у шапці `scripts/fs-proxy.mjs`; загроза — `SECURITY.md`, T-2.

**Дитина отримує канонізований шлях, а не написання клієнта.** Раніше проксі
канонізував шлях, щоб *перевірити*, але форвардив оригінал — сервер резолвив
той самий рядок удруге, своїми правилами. Перевірили одне, відкрили інше:
класичний обхід фільтрувального проксі. Тепер `enforce()` повертає переписані
аргументи, і `tools/call` форвардиться з ними:

```js
msg.params.arguments = args;  // дитина відкриває рівно те, що ми дозволили
```

Друга резолюція зникає — лишається одне тлумачення шляху, те, що співпало з
allowlist. Побічний ефект: дозволений файл тепер читається за будь-якого
написання (`UPPER-CASE`, 8.3-ім'я, traversal).

Виявив це тест: два кейси `want=pass` давали `got=child-denied` — проксі
пускав, сервер відмовляв. Старий асерт («аби не проксі») це приймав, тож
розбіжність між рівнями лишалась невидимою. Тепер `want=pass` вимагає, щоб файл
**справді прочитався**:

```js
const pass = want === "deny" ? refusedByProxy : got === "allowed";
```

З тимчасово вимкненим переписуванням тест червоніє рівно на тих двох кейсах —
асерт має зуби. З переписуванням 13/13 зелені, усі `want=pass` → `got=allowed`.

**Чому це не безпека.** `roots` — механізм координації: сервер *SHOULD* їх
поважати, не *MUST*. `server-filesystem` 0.2.0 поважає — перезаписує свій
allow-list. Сервер, який їх проігнорує, лишиться з `app/data`, і зупинити його
так само нічим. Справжня межа — права ОС.

**Що з цим зробили:** проксі (межа за шляхом) + `allow` з **двох** tools
(`read_text_file`, `list_allowed_directories`). `deny` на записові та
розвідувальні tools лишили, хоч проксі їх і не форвардить: це fail-safe на
випадок, якщо запис `filesystem` у `.mcp.json` колись повернуть до прямого
запуску сервера. Не робили: винести дані за межі проєкту; Docker із
`ro`-mount (справжній read-only, але межу шляхів roots усе одно перевизначить).

**Чому не `npx`.** Спочатку проксі запускав дитину через `npx -y <pkg>@версія`.
`npx` — не JS-файл, тож проксі йшов гілкою `shell: true` (Windows не дає
спавнити `.cmd` без шела — мітигація CVE-2024-27980), а Node на це попереджав
`DEP0190`: аргументи не екрануються, а конкатенуються в один командний рядок.
Тут вони всі з закоміченого конфіга, тож дірки нема — але компоненту, чия
єдина робота фільтрувати шляхи, не личить самому клеїти шел-рядок. Тепер у
`.mcp.json` стоїть прямий шлях до `dist/index.js`, і проксі спавнить його через
`process.execPath` — без шела взагалі. Тест `test:proxy` окремо перевіряє
відсутність `DEP0190`, щоб конфіг не з'їхав назад на шел непомітно.

Ціна: пакет тепер у `devDependencies` кореня, тож `npm run setup` робить ще й
`npm install` у корені, а свіжий клон без нього впаде на старті сервера
(«файла нема») замість того, щоб `npx` тихо стягнув пакет. Гучна поломка
замість тихої — але поломка нова. Натомість версію тримає вже
`package-lock.json` з хешем вмісту, а не тег, який можна перевипустити.

**Перевірено в хості після рестарту.** Хост читає `.mcp.json` на старті, тож у
сесії, де проксі додали, він ще не діяв — цифри нижче зняті вже в новій сесії:

| Виклик | Результат |
|---|---|
| `list_allowed_directories()` | `C:\...\app\data` — **аргумент, а не корінь репо** |
| `read_text_file(<repo>\app\data\catalog.json)` | ✅ прочитав |
| `read_text_file(<repo>\.env)` | ⛔ `Refused by fs-proxy: path is outside the allowlist` |
| `read_text_file(<repo>\app\data\..\..\.env)` | ⛔ те саме — traversal канонізується, а не порівнюється рядком |
| `tools/list` | **2** tools: `read_text_file`, `list_allowed_directories` |

Порівняй з таблицею в «Що з цього вийшло» вище: той самий хост, той самий
сервер, той самий `./app/data` в args — різниця лише в проксі.

Дрібниця, але показова: описи обох tools у хості несуть доданий проксі суфікс
`Restricted by fs-proxy to: …/app/data/catalog.json`. Модель бачить межу в
описі, а не дізнається про неї з відмови після спроби.

## Сервер 2 — memory (`@modelcontextprotocol/server-memory`)

| | |
|---|---|
| **Навіщо** | Тримати між сесіями факти, які не виводяться з коду: підсумки A/B (Task D), рішення по scope, ground-truth цифри. |
| **Транспорт** | stdio |
| **Запуск** | `npx -y @modelcontextprotocol/server-memory@2026.7.4` |
| **Scope** | Один файл — `.mcp-memory/memory.jsonl` (через `MEMORY_FILE_PATH`). Доступу до ФС **немає взагалі**: жоден tool не приймає шлях. Історія з `roots` його не стосується — межу тут тримає відсутність такого tool'а, а не перевірка шляху. |
| **Права** | Read-write свідомо — запис у власний граф і є функцією сервера. Але **тільки додавання**: `create_*`/`add_observations` в `allow`, усі три `delete_*` — у `deny`. Сенс сервера в тому, що факти переживають сесію; тихе видалення накопиченого — головний спосіб це зламати. Якщо треба почистити граф — руками в `memory.jsonl`. |
| **Секрети** | Немає токенів. `MEMORY_FILE_PATH` = `${MCP_MEMORY_FILE}`; значення машинозалежне, тому змінна, а не літерал. |
| **Версія** | Зафіксована `@2026.7.4`. |

> ⚠️ Шлях **має бути абсолютним**: відносний резолвиться не від cwd, а від
> каталогу пакета в npx-кеші. Значення задає лише
> `.claude/settings.local.json` → `env.MCP_MEMORY_FILE`; `.env` хост не
> читає — перевірено.
>
> Тут раніше стояло, що fallback у `.mcp.json` не потрібен, бо без
> значення «сервер не стартує, а не мовчки пише в кеш». **Припущення
> не підтвердилось** — стартує і пише. Механізм, відтворення й
> наслідки — [`SECURITY.md`](./SECURITY.md), загроза **T-1**.

**Tools (9):** `create_entities`, `create_relations`, `add_observations`,

## Сервер 3 — catalog (власний, `mcp-server/`, Task B)

| | |
|---|---|
| **Навіщо** | Дати моделі відповіді на питання, які не виводяться роздумом: що треба перезамовити та яка загальна вартість запасу. Це й є експеримент Task D. |
| **Транспорт** | stdio |
| **Запуск** | `node ./mcp-server/dist/server.js` |
| **Scope** | Власного доступу до ФС немає. Жоден tool не приймає шлях; єдиний I/O — `loadCatalog()` з імпортованого `app/dist/index.js`, який читає один файл. Історія з `roots` його не стосується — межу тримає відсутність tool'а, що бере шлях. |
| **Права** | Read-only за конструкцією: write-шляху в коді немає взагалі. Усі 4 tools позначені `readOnlyHint: true`, `destructiveHint: false`, `openWorldHint: false` — але це **самодекларація**, не гарантія (та сама історія *SHOULD*, що й із `roots`). |
| **Секрети** | Немає жодних. |
| **Версія** | SDK v2, `@modelcontextprotocol/server@^2.0.0`. |

**Tools (4):** `search_inventory`, `check_stock`, `low_stock`,
`inventory_summary`. **Resource:** `inventory://catalog`.

Доменна логіка **імпортована** з `app/`, а не переписана: сервер — тонкий
адаптер, і правило «що таке low stock» живе в одному протестованому місці.
Повний опис — [`mcp-server/README.md`](../../mcp-server/README.md).

**Працює — перевірено трьома незалежними клієнтами.**

1. **Власний скрипт:** `npm run check` з кореня репо запускає сервер по stdio
   так само, як це робить хост, і звіряє відповіді з ground truth. Віддає
   4 tools і 1 resource; `low_stock` — ті самі 9 SKU, `inventory_summary` —
   `totalInventoryValue: 46152`. Скрипт рахує ground truth з `app/dist` під
   час запуску, а не тримає зашиті числа — інакше він перевіряв би сам себе.
2. **MCP Inspector** — сторонній клієнт, написаний під специфікацію, а не під
   мій сервер (команда — в [`mcp-server/README.md`](../../mcp-server/README.md)):

   | Метод | Результат |
   |---|---|
   | `tools/list` | 4 tools, усі з `readOnlyHint: true` |
   | `resources/list` | `inventory://catalog`, `application/json` |
   | `tools/call low_stock` | `count: 9`, ті самі SKU |
   | `tools/call inventory_summary` | 24 товари, 7 категорій, `totalInventoryValue: 46152` |
   | `resources/read inventory://catalog` | 24 товари, коректний mime |

3. **У хості:** після рестарту Claude Code tools сервера `catalog` видно у
   списку — перевірено вручну.

Чому саме три, а не одна. Пункт 1 — мій власний код: якби мій сервер і мій
скрипт помилялись однаково, вони б **узгоджено** помилялись, і перевірка нічого
не доводила б. Inspector цю петлю розриває: він нічого не знає про мої
припущення. А пункти 1–2 разом усе одно нічого не кажуть про те, чи підхопив
сервер **хост** — це окреме питання, і ламається воно найчастіше (див. блок
нижче). Тому потрібні всі три.

> Inspector теж запускається з кореня репо — той самий баг із відносними
> шляхами, що й усюди в цьому розділі. Симптом і фікс — у таблиці «Якщо щось не
> працює»: [`mcp-server/README.md`](../../mcp-server/README.md).

> ⚠️ **Сервер мало зареєструвати в двох місцях, не в одному.** Запису в
> `.mcp.json` не достатньо: в `.claude/settings.json` стоїть
> `enableAllProjectMcpServers: false`, тож імʼя сервера має бути ще й у
> `enabledMcpjsonServers`. Інакше хост **мовчки** ігнорує сервер — без
> помилки, просто без tools. Це рівно той випадок «сервер працює, а хост
> його не бачить», про який попереджає walkthrough.

## Що НЕ підключали

- **`git` і `fetch` (uvx)** — потрібні Python + `uv`, яких немає. Окремо про
  `fetch`: тягне довільний контент із мережі в контекст — класичний вектор
  prompt injection, брати «за компанію» було б рівно тією помилкою, від якої
  застерігає Task C.
- **filesystem зі scope на корінь репо** — відхилили: для Task D потрібен лише
  `catalog.json`, ширший scope відкрив би все дерево разом із `.env`.
  **Спершу рішення не виконалось** — хост через `roots` дав саме корінь репо; тепер
  його виконує проксі, який roots не пропускає. Раніше `.env`
  читається через MCP-канал зараз; від запису тримає лише `deny`. Лишаю як
  приклад рішення, ухваленого на рівні, який його не вирішує.
- **`@latest` у `npx -y`** — те саме рішення про довіру, відхилено.

## Підсумок

- **Де можна читати** — вирішує **хост** (roots = корінь репо), не аргумент.
- **Хто перевіряє** — **сервер** (`lib.js:67`); `$HOME` недоступний.
- **Що можна викликати** — вирішує і виконує **хост** (`allow`/`deny`, 3 tools
  із 14). Без цього рівня read-only не існує: усередині межі сервер пише вільно.
- **Справжня межа** — права ОС. Решта — домовленість, яку сервер *SHOULD*, а
  не *MUST* дотримувати.

Планувалось «конфіг сервера задає *де*, права хоста — *що можна*». Насправді
**і те, і те задає хост**, а конфіг сервера в цьому хості не задає нічого — і
видно це лише тоді, коли перевіряєш сервер очима хоста, а не напряму.
